## 1. The design prompt (what the lead software designer was asked to do)

> You are the lead software designer for Arsenal Pro, a no-build PWA (plain ES modules, GitHub Pages, CSP `script-src 'self'`).
> 1. **Map every file into a zone.** For each zone: the files it owns, its public interface (the only files another zone may import), which zones it may import, and the tests that cover it. Zones: ENGINE, SCORING, EVENT_LOG (locked); CATALOG; BAG; ARSENAL; LANE/OPTIMIZE; LOG BOOK; ADD A BALL; GAME; SHELL/router/SW; UI theme; TESTS; and whatever else the code shows.
> 2. **Draw the lines in code.** A Node script, no npm deps, no build step, that parses imports and fails when a zone imports another zone's internals. Fix violations or list them as documented exceptions with a reason. **Do not change behavior.**
> 3. **Lock the three zones that must not drift.** SHA-256 manifests of the engine, scoring and the event-log schema. A change fails unless a deliberate unlock entry (file, reason, date) is in `docs/LOCKS.md`. `simulatePath` stays unchanged; equivalence stays 7500 / 0.
> 4. **Scope the checks to the change.** One command takes the changed files, works out the touched zones and runs only those zones' tests plus the boundary check, the lock check and a fast smoke. A locked-zone, SHELL or service-worker change escalates to the full suite by itself. Document before/after timings.
> 5. Optionally add a light CI step, as long as it needs no token-scope change.
> Constraints: no app behavior change, no new dependency, no service-worker version bump unless a shipped file changes, offline-first and CSP untouched, never force-push.

## 2. How the zones work

- A **zone** owns files (patterns in `tools/zones/zones.json`; first match wins; every tracked file must be owned).
- A zone's **public interface** is a list of files. Another zone may import a file of this zone only if it is on that list.
- A zone's **allow** list names the zones it may depend on (layering). Anything else is a violation, even through a public file.
- A zone's **route entries** are its lazy-loaded screens. Only the SHELL router (`js/main.js`) imports those.
- The pure Command-Center logic in `js/cc/*.js` is the public face of a zone; its DOM screens in `js/screens/*.js` are internal unless listed as public (a few shared sheets are).
- Imports are checked for `js/**` (static, re-exports and literal `import()`); `js/vendor/**` is third-party code and not scanned. Bare or remote specifiers fail (CSP, no build step), and so does a dynamic `import()` the checker cannot read.

Layers, bottom to top:

1. **Kernels** (import nothing above them): SCORING, EVENT_LOG (imports SCORING), CATALOG, ENGINE (imports CATALOG).
2. **State:** PERSISTENCE (store, hub, sync, backup, recovery, profile, device features) depends on the kernels and the SHELL UI kit.
3. **Features:** BAG, LANE, GAME, LOGBOOK, ARSENAL, ADD_BALL, IMPORT, ME depend on the kernels, PERSISTENCE, the SHELL UI kit and a few named sibling zones (listed per zone below).
4. **SHELL** routes to every feature (through route entries only) and offers the UI kit, router and help to all.
5. **THEME, TOOLING, TESTS, DOCS** have no imports.

Feature zones talk to each other only through public files, and only along the allow lists below.

## 4. Locks

Locked: `js/engine.js` (with `simulatePath`), the equivalence oracle (`tests/engine_equivalence.mjs`, `tests/fixtures/engine-inputs.v64.json`, `tests/legacy/app.v1.js`), `js/data/scoring.js`, and the event-log schema (`js/data/schema.js`, `js/data/events.js`, `js/data/migrate.js`). `js/data/project.js` is in the EVENT_LOG zone (any change runs the full suite) but is not hash-locked, because it changes with features.

The pins live in `tools/zones/locks.manifest.json`. The lock test is part of `tests/data/zones.test.mjs`, so the existing CI unit-test step enforces it. **How to unlock:** see [LOCKS.md](LOCKS.md): `node tools/zones/locks.mjs --unlock <file> --reason "why"` re-pins the file and logs the reason, date and new hash in one step; commit them with the change. Editing only the pin, or only the log, fails.

## 5. Zone-scoped quick check: `node tools/check.mjs`

```
node tools/check.mjs                # changed files = git diff origin/main...HEAD + working tree; runs the plan below
node tools/check.mjs --dry-run      # print the touched zones, the escalation reasons and the steps; run nothing
node tools/check.mjs --full         # force the full suite
node tools/check.mjs --no-browser   # node-only steps (no Playwright needed)
node tools/check.mjs --files a,b    # pretend exactly these files changed
```

**Always:** boundary check, lock check, engine equivalence (7500 / 0), the `node --check` syntax pass on changed JS.

**Quick mode (zone-scoped):**

| Step | What runs |
|---|---|
| Unit tests | the touched zones' declared unit tests, plus any test that depends on a changed file (transitively, found from its imports and the app paths it reads), plus changed test files |
| Budget | `tests/perf_budget.py` (no browser: bytes, module count, SW list, replay time) when a shipped file changed |
| Fast smoke | `tests/home_game_flow.py` (Bag, game, Log book) when a shipped file changed |
| Zone journeys | the touched zones' journeys (for example LANE runs J03 and J12), batched into one `run.py --only` run without visual baselines |
| Theme | a THEME change also runs the visual baseline comparison |
| Zone smokes | ADD_BALL runs the spec-chain smoke; PERSISTENCE runs the recovery and foundation smokes |
| Docs, tests, tools only | boundary, lock, equivalence and the changed tests; no browser |

**Escalates to the full suite automatically** when: a locked file changed; any file of ENGINE, SCORING, EVENT_LOG or SHELL changed (index.html, router, UI kit, `sw.js`, `.github/**`); four or more feature zones are touched (an app-wide change); a file has no zone (it cannot be scoped); or `--full` is given.

**Full suite** = what CI runs: engine equivalence, all unit tests, `e2e.py`, the local recovery smoke, the journeys with the visual baselines, plus the performance budget. CI still runs everything on every push; `tools/check.mjs` is the local pre-push loop. A Lighthouse-only failure in CI is not part of the local check.

## 6. Working with the zones

- **New file in `js/`:** add it to a zone's `owns` in `zones.json` (the boundary check fails on an unowned file). If another zone needs it, add it to `public`.
- **New unit test in `tests/data/`:** add it to the `unit` list of the zone it covers.
- **A new cross-zone import that the check rejects:** first ask whether the code is in the right zone, or whether a public file should be used. Only then add an exception with a real reason; exceptions are meant to shrink.
- **Changing a locked file:** `docs/LOCKS.md`.
- **Shipped files changed?** Then the usual rule applies: bump the service-worker cache name and run the journeys. This design touched no shipped file, so no version bump.

## 7. Boundary violations found
