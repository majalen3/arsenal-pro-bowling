# Arsenal Pro 2.0 — Decisions record

Short ADR-style notes. Each: decision · why · consequence.

1. **Leave the single file; ES modules, no build step.** v1 was one ~3k-line `index.html`. 2.0 is `index.html` + `css/app.css` + `js/*.js` native ES modules with a hash router and lazy-loaded screens (`import()` per route), plus `<link rel=modulepreload>` for the lane path. *Why:* GitHub Pages hosting, CSP `script-src 'self'` kept unchanged (no inline script, no eval), nothing to install to contribute. *Consequence:* no minifier — budget met anyway (see cycle log), files are served as-is.
2. **Engine is a verbatim port.** `js/engine.js` holds `simulatePath`/analysis copied from v1; `tests/engine_equivalence.mjs` runs the v1 function and the module on 7 500 input combinations and requires 0 mismatches (also in CI). Lane geometry and the coach voice are unchanged.
3. **Miss buttons vs coach advice.** The “Your ball went” buttons apply the v1 adjustment rules (e.g. Left → feet +2, target +1) with Undo; the coach line remains the engine’s read of the *current* line. They can disagree for one shot (rules are the user’s observation, the coach is the model). We show the rule move on the button (“Missed left: move feet 2 left…”) so the user sees exactly what changes.
4. **Moving feet keeps the target board.** In the Tune sheet, lane drag and arrow keys, a Feet change re-derives aim so the arrows target stays put (`adjust({release, keepTarget:true})`); editing Target changes aim only. *Why:* bowlers move feet and eyes as separate decisions; v1 stored release+aim, so we derive target = release − aim and keep the stored shape. Miss buttons are the exception — they apply the 2-and-1 rule to both.
5. **Legacy tests moved to `tests/legacy/`.** They drove v1 DOM ids and `app.js`, which no longer exist. Replaced by `tests/e2e.py` (phone + desktop jobs, axe, 44 px, offline, v1 migration, pin deck) and the engine equivalence test. CI (`.github/workflows/ui.yml`) runs both.
6. **Pattern library vs lane presets.** The lane model has six oil presets. Library patterns (Kegel library via CarryDown) are mapped to the nearest preset by length; the pattern page says so explicitly (“approximation”).
7. **Onboarding collects more than the engine uses.** Hand, style, speed, rev; PAP/tilt optional. Speed and rev feed the lane. Hand mirrors the pin-deck view (1-2 pocket, mirrored pin numbers); the lane canvas itself stays in v1 right-hand board coordinates and a note says so. Style/PAP/tilt are stored for future use and never invent effects. Existing v1 users (any `ap_state`) skip onboarding.
8. **Local shot log.** Each miss tap is appended to `ap_shots` (local only, keeps the most recent entries; shown in Sessions → Shots). Not sent to the API — no endpoint exists for it and we did not add one.
9. **localStorage migration without loss.** v1 keys (`ap_state`, `ap_lines`, `ap_surface`, `ap_notes`, `ap_dels`, `ap_device` backup code) are read in place with the same shapes; new keys (`ap_profile`, `ap_prefs`, `ap_shots`) are additive. Offline save queue and backup code behave as in v1; endpoints unchanged.
10. **Service-worker updates.** Network-first shell with cache fallback; API never cached. New versions wait and the app offers “Update”; exception: clients coming from the v1 SW cache (`arsenal-pro-v2`) activate immediately because v1 has no update prompt. Cache name bumps with each shell change.
11. **Pin deck: approximate 2-D pin-action model (cycle 5).** The engine still predicts only entry board and angle at the head pin; `simulatePath` is unchanged. After first contact, `js/pinsim.js` runs a labelled frictionless 2-D impulse model: the Kickertz/Stronge method, with USBC pin weight 3 lb 8 oz, COR 0.670 and dimensions, and an *assumed* 15 lb ball. It checks qualitatively against the USBC Pin Carry Study (2009) strike types. The UI says “Model” and “approximate” and links to docs/DEFLECTION.md, which lists sources, assumptions and known gaps (no hook on the deck, no pin tipping, no kickbacks). Strike/light/high colouring still comes from the engine call. (Before cycle 5: straight dashed projection, “no deflection”.)
12. **HTTP caching.** GitHub Pages sends `max-age=600`; the SW’s network-first fetch makes deploys visible on next load online, and keeps everything usable offline.
13. **Tests never write to production.** All browser tests abort requests to `arsenal-pro-api.onrender.com`. (Early in the 2.0 work two test lines, ids 1003/1004 ("House 14→17", created 2026-10-23 02:29:26/02:29:36 UTC from two throwaway device codes), were written before this was enforced. With the owner's approval they were **deleted on 2026-10-23** through a temporary endpoint in arsenal-pro-api (commit bdd2d81) gated by a one-time `ADMIN_TOKEN` set via the Render dashboard API. The endpoint deleted only rows whose id, name and `created_at` all matched, inside a transaction that rolled back on any mismatch. It returned exactly 1003 and 1004, a re-read returned no rows, and the endpoint was removed in 669e71a (deploy live, `/api/admin/test-lines` → 404). `ADMIN_TOKEN` was then blanked. No other rows were touched.)
14. **v1 data layer: an append-only event log is the source of truth (D0, 2026-10-23).** `js/data/` (DOM-free, `node --test tests/data/`) holds the envelope (`events.js`), the fold to a projection (`project.js`, per-field last-writer-wins by ts then id), validators, USBC scoring, the v0 migration, the IndexedDB/localStorage/memory backends and v1 backups. The log lives in IndexedDB `arsenal-pro` (falls back to localStorage `ap_v1_*`, then memory). *Why:* history, undo of whole imports, and sync without loss. *Consequence:* the `ap_*` keys stay as the hot mirror that the existing screens and the v1 API read; every write in `store.js` is dual-written through `record()` into the log. The log opens after first paint (`main.js` imports `hub.js` after `start()`), so the lane is never blocked: measured 32 ms open+migrate in e2e. Decision #8's "keeps the most recent entries" is void: no list is truncated any more.
15. **v0 → v1 migration is idempotent and loses nothing.** Event ids are `m0-` + a hash of (key, index, content), so re-running adds 0 events. The raw `ap_*` snapshot is kept in `meta.legacySnapshot` and goes into every v1 backup. Pattern notes have no date in v0: they migrate with `date: null`, never deduped. v0 shots become one synthetic "legacy-YYYY-MM-DD" session per day. A v0 backup file restores through the same migration. Writes made between first paint and the log opening are dropped from the queue when migration ran, because they are already inside the migrated snapshot.
16. **Restore rebuilds only empty mirror keys.** After a restore, each empty `ap_*` key is rebuilt from the projection. A key that has data is never overwritten. Boot does not do this, so clearing site data by hand is not silently undone.
17. **Reported arsenal seed (2026-10-23).** The owner's reported bag (benchmark Rattler Big Bite; Tournament 6 = Big Bite, Super Nova, Ordnance C4, Hy-Road Pearl, Deadly Rattler, Ice Storm; League 3 = Big Bite, Hy-Road Pearl, Ice Storm; also owned Guru Supreme, Raw Hammer Black, Scout Reactive, Rack Attack) is one undoable import `seed-owner-2026-10-23`, every field `user-reported`. The owner said "Hy-Road"; it is mapped to the catalog's Hy-Road Pearl. Rack Attack is "type unverified" and is not linked to the catalog's `rack-attack` urethane entry. Release: RH tweener, ~15 mph (measurement point unknown), ~220 rpm, PAP 5⅛" (horizontal only), medium tilt and rotation. *Because the site is public*, the seed loads automatically only on a phone that already has app history (the owner's) and only when no owned balls exist; a fresh phone gets a one-tap "Load starter arsenal" offer instead, so strangers never inherit someone's bag. Undo removes it everywhere.

18. **Import pipeline: plans are pure data (D1, 2026-10-23).** `js/data/importer.js` turns a file into a plan (parse → validate → match → dedupe) without touching storage; Import writes `plan.events` in one append, Undo appends `import.voided`. The raw file is never stored: only name, size, SHA-256 and a semantic key (order-free hash of the parsed rows) so a re-saved copy is still caught. Score files are read with the shape rules ported from Bowling-HQ (`Game N` columns, frame/shot rows scored with USBC rules, score column, plain numbers); row errors are collected and shown, never thrown. Spreadsheet formula cells are read as text and flagged; CSV export neutralises them. Fuzzy ball names must be confirmed ("Big Bite → Radical Rattler Big Bite?"); exact aliases auto-fill but stay editable; a name not in the catalog can be kept as text with no ball link. Speed columns require an explicit measurement point (release/launch/average/impact/not sure) because those differ by 1–3 mph. Release numbers from CSV become `releaseMeasurement` rows, never profile values, until accepted. The Ruby preset is a stub (`awaiting-sample`): no columns are guessed until a real export is provided.

19. **LaneTrax: the user's own exported session report, parsed on the phone (D2, 2026-10-23).** The only LaneTrax path is "Import your LaneTrax session report (PDF)": a file the user exported and picked. No scraping, no calls to LaneTrax servers, no reverse-engineering of their app, no stored credentials. `js/data/lanetrax.js` reads the PDF's text (Flate streams, ToUnicode CMaps, `Td`/`Tj` positions; images are never decoded) and accepts it only when page 1 carries the "LaneTrax Session Report" title **and** the producer is jsPDF; anything else is refused before a plan exists. It keeps **session-level stats only**: Key Stats, outcome counts and the Summary table (mean and range). The per-shot charts are images, so 0 per-shot values are created. Inconsistencies inside the report are import warnings and both values are kept: `SHOT_COUNT_GAP` (strikes + leaves + spares = 86 vs 90 total shots) and `IMPACT_SPEED_KPI_VS_TABLE` (13.93 vs 13.0 mph). Units: kph and m/s are converted to mph and metres to feet, and the printed value is kept in `orig`. The report's unit settings are stored, and handedness is `null` because the report doesn't print it. Boards are read as printed (RH). A "Flip boards" toggle maps board *positions* b → 40 − b (arrows, breakpoint, entry, foul line); hook-board counts and ranges are not flipped. Release numbers (launch/average/impact speed, rev rate) become pending `releaseMeasurement`s (`accepted:false`). The profile changes only when the user taps Accept on Tonight (`releaseMeasurement.accepted`). Provenance chip: "LaneTrax · date · n=?", since the report doesn't say how many shots each average covers. Tests use a derived, anonymised words fixture plus a synthetic PDF built from it at test time. The real report is never in git; its decode test runs only with `LANETRAX_SAMPLE=…`. Not done: a warning for range artefacts (e.g. a 36.7-board entry range from a tracking glitch). No rule could be justified from one sample.

20. **Sync v2: event outbox to `/api/events` (D3, 2026-10-23).** Every event is written to the on-phone log first and pushed later from an outbox (`js/data/sync.js`, DOM-free and tested against a mock server). Client batches are ≤ 15 kB and ≤ 500 events; the server keeps its 20 kB body limit, so an oversized body still gets **413** (the v1 contract) and the client splits it. Pushes are idempotent (`ON CONFLICT DO NOTHING` on (device, id)), so a lost response never duplicates. Backoff is 15 s / 45 s / 120 s / 300 s, or `Retry-After` when the server sends one. **Quota: 5 000 events per backup code → 429** with `{error, quota, stored}` and *no* Retry-After; the phone stops pushing (no retry loop), keeps everything locally, and More explains it with a backup-download hint. We read "20 kB/batch → 429" in the brief as: count quota → 429, byte limit → 413, because a 429 on size would make every v1 client retry forever. A single event the server refuses (400) is set aside in `sync.rejected`, not retried. Pull is cursor-paged (500 × up to 40 pages); pulled events are marked synced and are never pushed back. Each event keeps its writing phone's `seq` (server column `src_seq`, additive) so same-millisecond events fold in the same order on every phone; `serverSeq` is only the cursor. Changing the backup code marks everything unsynced and re-pushes to the new code. The v1 endpoints (`/api/lines`, `/api/surface-log`, `/api/pattern-notes`) are still dual-written for older installs; pattern notes gained `?limit&before` paging. `/api/me` export and delete include `events`.

21. **Tonight: rank only your own bag, explain every number (CC0, 2026-10-23).** `js/cc/rank.js` is pure and tested with 26 golden scenarios. **Demand (1–5):** length band ≤36 short / 37–41 medium / ≥42 long → base 2/3/4. Volume adds −1/0/+1 by the pattern library's own mL tertiles (26.05 / 28.7 mL across 709 Kegel patterns, not a magic number). Wood −1, synthetic 0, unknown 0 (flagged "assumed"). Transition −1, burn −2. The result is clamped to 1–5. All of these are team rules (A), shown as such. **Ball level (1–5)** comes from the catalog's oil tag (heavy 5 … light 1), labelled "app tag", because there is no maker condition field for these balls (physics `ball_specs.csv` has no usable match). A ball with no catalog link (Rack Attack) gets no level, shows "spec TBD", sorts last and gets 0 model lines. **Order:** benchmark first when the pattern is unknown, the center is new, or it is game 1 with a tournament bag. Then closeness to demand, shape fit by style (stroker → asym, cranker → sym), cover (solid > hybrid > pearl > urethane), duller surface, lower RG, higher diff, then name. The spare ball and pro-shop/retired balls are never ranked. **Reads** move one step: early → weaker, weak → stronger, angular/smooth → the nearest ball within ±1 level on a shape proxy (pearl +2, hybrid +1, solid 0, urethane −1, asym +1, diff ≥ 0.05 +1; labelled an estimate). **Rule of 31** uses the real pattern length. For ≥ 42 ft bowl.com's 13–16 band is shown too, and when they disagree both are shown, not averaged. **Model line:** the unchanged engine on the nearest preset by length (the Pattern screen's approximation), searched over feet 5–30 × aim ±8 for a strike nearest the Rule-of-31 board, with "holds x of 6" over ±0.5 mph / ±20 rpm / ±1 board. Engine globals are restored after every call. **Session** is `session.created/edited` id `tonight-YYYY-MM-DD`; a center is `center.created`. **LaneTrax accept** appends `releaseMeasurement.accepted` and a `bowler.edited` with device provenance ("LaneTrax · date"); nothing changes the profile without that tap. **Tonight is a new first tab**; the default route stays the Lane, because the e2e suite and v1 users land there.

22. **Quick log on Tonight: one event per ball, pins you can see (CC1, 2026-10-23).** The quick log is a card under the pick on Tonight, not a separate screen, because the pick, the read buttons and the log are used together between shots. Each delivery appends one `shot.logged` {sessionId, game, frame, roll, down, leave[], foul, split, ballId, catalogId, miss} to IndexedDB, and the screen redraws from the projection only after the write resolves. So whatever the screen shows has already survived a tab kill (e2e kills the tab, reopens, and compares frames). **Taps:** X = 1. For a leave you tap the standing pins, then "Log n standing", then "/" (or "– Missed all"), which makes a one-pin spare 3 taps. Undo appends `event.voided` (append-only log; sync and export see it). **Fouls** score 0, and a first-ball foul respots the rack (USBC). **10th frame:** the third ball is offered only when earned, on a fresh rack after X or /. Scoring stays in `js/data/scoring.js`; `js/cc/quicklog.js` only tracks frame, ball, pins facing and marks. **Splits** use the USBC Rule 2h reading in `isSplit`: 2-7 and 3-10 (baby splits) count, sleepers like 2-8 don't. A split shows ○ in the frame. **3-6-9 per leave:** the key pin is the one nearest the bowler. Two key pins in the same row (7-10, 4-6) show both moves, because the system has no single answer for them. The strike board is 20 until the user sets theirs (gap). **Triggers** use the last 3 first balls of the session; untagged balls count as "not high/light". The optional "First ball hit" tag (Pocket/High/Light) feeds them, and 2 "too early" reads still give Plan B. The thresholds stay the CC0 team rule (A).

23. **Bag builder: warnings, not walls; fill from what you own (CC2, 2026-10-23).** `#/bag` opens from Tonight ("Bag builder ›") and keeps the Tonight tab current. The rules live in `js/cc/bag.js` (pure, unit-tested), and every change appends one `bag.saved` with the full bag {name, format, slots[{owned, locked}], spare, excluded[], eventDate}, so lock/exclude/swap sync and export like any other event.
   - **Coverage grid:** strength 5→1 comes from the app oil tag (`levelOf`, the same scale Tonight uses). Shape is smooth/medium/angular from the CC0 angularity proxy (≤1 / 2 / ≥3) and is labelled **"shape (estimate)"**, because no maker shape spec is held. Balls with no catalog match (Rack Attack) sit in a "Spec TBD" row and are left out of overlap/hole maths.
   - **Overlap** means the same cell, or the same core name with the same cover type. **Hole** means an empty level strictly between the strongest and weakest ball. On the reported bags, HRP and Deadly Rattler overlap (both level 2, medium) and League 3 has a hole at level 3.
   - **The 10 checks are all warnings:**
     - benchmark (exactly one, in the middle)
     - spare (for league/tournament formats)
     - overlap and hole
     - pattern fit (each of fresh/transition/burn demand within ±1 level, only once a pattern is set)
     - sym/asym mix by style
     - control option for short (≤36 ft) or flat (≤3:1, A) patterns, where control means urethane or level ≤2
     - service due before the event
     - pro-shop/retired left off the pack list, with the reason
     - USBC: "check the approved list" only for balls not matched to the catalog; the device holds no USBC list, so it never claims a ball is approved
   - **Fill bag** draws only on owned balls that are not pro-shop, retired or excluded. Locked balls always stay in and the current spare is kept. Sizes are League 3 = 2+spare, League 4 = 3+spare, Tournament 6 = 5+spare. It brute-forces the combinations, scoring warnings ×10, overlaps ×3, holes ×2, minus level span, minus 5 for a benchmark, plus 4 per spec-TBD ball, minus 0.5 per ball already carried (a tie-break toward the smallest change). The result is shown as an In/Out diff before anything is saved.
   - **Swap** is 2 taps (ball in the grid, then the replacement). Candidates are sorted by level distance.
   - **Care:** due rules are the cited defaults in ARSENAL_MANAGER_PLAN §1.4, by brand family:
     - Radical counts as Brunswick: refresh 10, resurface 60, detox 60.
     - Storm and 900 Global: 25 / 60 / 60.
     - Hammer: resurface 50, marked unverified.
     - Motiv: 50.
     - No guidance (Columbia 300) uses the conservative Brunswick values, labelled as such.
     - Urethane detox is off.
     - Items fire 6 games early (A, about two league nights).
   - **Health counts** are `healthOf(projection)`, i.e. a fold over logged games and `ball.serviced` events, and are never typed in. When a ball has never been serviced, the count is "≥ games logged". Ball status (In bag / Benched / Pro shop / Retired) is an `ownedBall.edited`, and service is logged from the same card.

24. **Add a ball: catalogue first, maker page second, the user confirms, the engine compares (AB, 2026-10-23).** `#/add-ball` opens from Arsenal ("Add ball") and the Bag screen. **Find:** a typed name is matched against 167 entries: the app catalogue (`data.js`, with USBC approval dates where USBC lists them) plus 145 rows derived from the bowlingballvideos.com catalogue (`js/data/spec_catalog.js`, generated by `tools/build_spec_catalog.py`; the raw CSV stays out of git). Matching is canonical (case, punctuation, roman numerals, squashed spaces), then fuzzy (Dice + one-edit token equality). A detected brand scores only the model words, and other brands get ×0.6, so "Storm Phaze 2" can't match a random Storm ball through the word "Storm". An app entry wins a name clash with a CSV row. **Look up:** `GET /api/spec-lookup?brand&name|url` (API f0ef954) fetches only allowlisted maker hosts (10 brands; Motiv returns `unsupported`), over https, with no login and no stored credentials. It parses RG/diff/int diff per weight, cover, finish, core and symmetry, and caches the parsed result (never the raw page) in `spec_cache` with the source URL and the read date. `spec_cache` holds no user data, so `/api/me` export and delete don't need to cover it. **Confirm:** every value carries its source chip (maker host + "16 lb" note, "catalog", "USBC", "calc" for derived cover type, or "you"). Anything not printed reads "spec TBD"; nothing is estimated into a spec field. Weight-specific values follow the chosen weight. When the chosen weight isn't printed, the printed value is shown with an "other weight" flag. **Maker wins** over the catalogue; each disagreement beyond the tolerance (RG 0.005, diff/int diff 0.002, text fields exact) is listed, never hidden. When the maker site returns several pages, the user picks one. Offline or on an error, the catalogue values stand, with a Retry button. **Engine card:** the unchanged `simulatePath` (via `analyze`) runs on the nearest preset for tonight's pattern length (or the assumed 38 ft house shot) at the bowler's speed and rev (or 15 mph / 220 rpm, chipped "assumed"). The release is the Rattler Big Bite's own model line, so the new ball and the bench get the same release, and the card shows skid/hook/roll, breakpoint and entry angle side by side plus the new ball's own line. Engine globals are restored. No RG/diff, no symmetry, or a plastic cover → no engine run ("spec TBD"). **Placement:** the same 5×3 grid as `#/bag`, with overlap and hole notes for the new ball. When the maker gives no oil condition, the user picks the level (prov "you"). **Save:** one `ownedBall.created` {catalogId, added:true, status:'benched', weight, spec{cat, fields, src, entryId, conflicts}} (<8 000 chars). `js/cc/cats.js` registers added balls, so Tonight, Bag, rank and model resolve them like catalogue balls. cc3d stays off.

25. **Targeting + Find my strike line: cited rules on the unchanged engine, Pocket % only (TG, 2026-10-24).** `#/target` turns feet, drift, ball offset and eyes (arrows or dots) into a laydown and an arrows board, then runs them through the unchanged `analyze` (engine equivalence 7 500/0). `js/lane.js` changes are renderer-only.
    - **Break box:** ±1.5 boards × ±1 ft (HK "three-board area"; NBA house shot 8–10 at 39–41 ft).
    - **Pocket call:** the engine's strike rule.
    - **Moves:** cited move families are tried both ways on the engine, and the smallest one that improves the shot is offered. When the engine's direction contradicts the house-shot "move toward the miss" rule (bowl.com, NBA), the card says so rather than hiding it.
    - **Find my strike line:**
      - A grid over laydown × arrows target, then 200 seeded Monte Carlo shots per top-10 line.
      - Arrows spread is measured from LaneTrax "Average Difference" (our reading: mean |miss|) when imported, otherwise assumed and labelled. Laydown, speed and rev spreads are assumed.
      - Pocket % = the share of shots entering boards 17–18 at 4–6°. The board-only window is used when no line reaches 4–6°. Source: USBC "I Left What Where?" via NBA, "the board decides regardless of angle".
      - **No strike % is shown**: the only published carry figure (85% at 17.5) is not a curve.
      - Lines with more miss room win ties (within 3 points).
      - It runs synchronously (70 ms at 4× throttle), so no worker is needed.

26. **Arrows geometry fixed; engine launch-angle and oil limits labelled, not hidden (TG-fix, 2026-10-24).** The v1 label `target = release − aim` (one board per aim unit) was about 10× too large. The engine's own path crosses the arrows (15 ft) at `release − 6.25·sin(aim°)` boards, so the full aim range of ±8 reaches only ±0.80 board. `js/cc/geom.js` derives that from the engine constants, and every layer (Lane drag and steppers, Targeting, Find, pickers, Sessions, the Tonight model line) now uses it. `simulatePath` is unchanged: equivalence is 7 500/0, and a unit test checks `arrowsBoard` against the engine path to within 0.05 board. Effect on Find (Big Bite, 15 mph/220 rpm, house, 38 ft): "Stand 18, aim 18, 60%" became "Stand 17, aim 11 at the arrows, 27%". The old Monte Carlo had shrunk a ±1.5-board miss at the arrows to 0.15 board.

    **Engine limitation (not fixable without changing `simulatePath`):**
    - The model's line is nearly straight to the breakpoint (at most 0.8 board off the laydown at the arrows). Real tweener lines swing 3–5 boards, e.g. 14–15 → 10 (bowlingball.com BowlVersity, search excerpt).
    - At 4 speed/rev profiles, no model line crosses 17–18 at 4–6° from a breakpoint on 8–10 near 39–41 ft, which is the NBA house shot (search excerpt).
    - The 3 flat oil zones mean a feet move slides the whole line, so the model can disagree with "move toward the miss".
    **Decision:**
    - Advice direction follows the cited rule (bowl.com/USBC; NBA: high → 2 left / 1 left; light → parallel 2 right).
    - The engine result is shown alongside as a model check (`modelAgrees`), and a disclosure is shown when the model says it would get worse.
    - Lane's coach sentence goes through `houseRule()` in the screen layer, because `coachLine` in engine.js is frozen. Lane's Left/Right miss buttons stay 2-and-1 toward the miss, now on the correct geometry (often clamped at the model's reach).
    - Targeting shows a "Model limit" panel with the cited book lines.
    - Recommended next step, needing owner approval: engine v2 with a real launch angle and an oil gradient.
    - **Independent check, and angles:** the independent engine verification (docs/ENGINE_VERIFICATION_REPORT.md 5a/5b) agrees with this verdict.
      - A unit test now asserts that Find's reported arrows board equals the engine path's crossing at 15 ft (< 0.1 board) for 6 balls × 3 speed/rev profiles.
      - Engine angles are drawn-lane units (a drawn 4–6° is about 1° real, per the report), so every user-facing angle now reads "° model" or "(model)", and Targeting's Model limit panel explains this (`LIMITS.angle`). The strike rule itself is unchanged.

27. **Bag Advisor: event first, owned balls only, results re-order only past 21 games (BA, 2026-10-24).** The first card on Tonight asks "Where are you bowling?" (League night / Tournament / Practice / New center / Sport pattern). One tap builds the bag with `js/cc/advisor.js`, which wraps `bag.fill` and `rank`, so the bag builder and the advisor can't disagree. Sizes are bag.js's 3 (league) and 6 (tournament); practice is 2 + spare and sport/new center reuse those formats (app choices, labelled). Only `inBag` balls are offered. Evidence per ball comes from the user's own `shot.logged`/`game.logged` (pocket %, strike %, sessions, n, most-left leave). The spec order changes only by adjacent swaps when both balls sit at the same demand distance and both have ≥21 games. 21 is borrowed from USBC Rule 319a (certified average minimum; bowl.com search excerpt) and shown as the source. Below that the chip says "app estimate (N of 21 games)"; with no data it says "specs only" and offers Quick-log/Import. One warning per ball: service due beats overlap. "Pack this" appends `bag.saved` `bag-adv-<event>` (source 'advisor') so the pack syncs/exports like any bag. The last answer per event lives in prefs. **Feet fix:** "Feet" on Tonight is now the stand (laydown + ball-from-foot offset − drift, from Targeting prefs or 7/0 assumed); the laydown is its own row. **Pins** became an 8-column grid with 2-column spans (≥48 px) because the old 44 px grid overflowed 360 px by 6 px. The e2e overflow checks were tightened (mobile emulation had widened innerWidth).

28. **Bowler Card, session results and Nights (BC, 2026-10-24).**
    - **One sentence first.** Import results and every session open on one headline change (average if it moved ≥5 pins, else spare/strike/open % if ≥5 points, else "about the same"), at most 2 supporting stats and one next focus (the worst leave with ≥2 chances, "the 10 pin, 3 of 4 made tonight"). Everything else is behind Details.
